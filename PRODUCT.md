# Product

<!-- impeccable:product-schema 1 -->

Scope: this file covers three reader-facing outputs and nothing else in the repo. The sections directly below cover the pages the `open-course` skill builds (`skills/learning/open-course/`): the Syllabus (`index.html`), and per Lesson a Handout and Slides. The `clean-comments` report and the `show-grill-clearly` questionnaire each have their own block at the end of this file. DESIGN.md and its sidecar belong to open-course only.

## Platform

web

## Users

- **Learners studying alone on a computer**: read a Handout for a long stretch, follow citation markers to the Source list, try the Exercises before opening the answers.
- **Learners on a phone**: the same Handout on a narrow screen, often in short sessions.
- **Teachers presenting Slides in a classroom**: a projector or large screen, students at the back must be able to read it, slides changed with arrow keys or a clicker (Page Up / Page Down).

Audience, level, and length differ per Course; the skill takes them from the user each time.

## Product Purpose

Turn a topic into a Course someone can teach from or study, where every factual claim cites a Source that was actually read while building it. Success: a learner can find their Lesson, read it comfortably for a long time, and check any claim against its Source in one click; a teacher can present without preparing anything else.

## Positioning

Every claim on every page traces to a numbered Source, and the build refuses a Course that breaks this. Citations are the product's spine, not a footnote.

## Operating Context

- Courses can be long: a 30-day Course means 30 or more Lessons on the Syllabus. The Syllabus must stay navigable at that size, not one long scroll.
- Pages open offline, straight from the file system or any static folder, in light and dark mode.
- Course language varies (`language` tag); Traditional Chinese on Windows is the primary real-world case and the one checked before release.

## Capabilities and Constraints

- Pages are generated by `scripts/build-course.mjs` from one course data file (JSON). The data format and the citation rules are fixed; page markup and styling may change.
- Every page is a single HTML file that loads nothing from the network: no web fonts by URL, no CDN, CSS and script inlined. CJK text uses system stacks; one Latin-and-numerals subset face is embedded in each page as a data URI.
- Avoid `system-ui` for CJK: on Windows in Chinese it falls back to PMingLiU.
- Slides work without script (all slides in turn); `slides.js` adds one-at-a-time presenting.
- Exercise answers stay folded until opened, without script.
- An Explainer video, when present, is an embedded player page per section.
- Tests in `tests/open-course/` check the built pages' structure and citations.

## Evidence on Hand

No real Course project is committed in the repo; tests use synthetic data. Design previews need a synthetic sample Course, labelled as such.

## Product Principles

1. Citation first: a claim and its Source are never more than one click apart.
2. Reading comfort over decoration: the Handout is read for long stretches, on desktop and phone.
3. Scales to long Courses: every page still works with 30+ Lessons or many sections.
4. Offline and self-contained: one file per page, nothing fetched.

## Accessibility & Inclusion

Dark mode is a first-class mode. Slides must stay legible from the back of a classroom.

# Product: clean-comments report

Covers the one HTML report the `clean-comments` skill (`skills/engineering/clean-comments/`) writes after a run. Its visual design is recorded in its surface brief and its own CSS, not in DESIGN.md.

## Platform

web

## Users

- **A developer who just ran `clean-comments` on their own repo**: the skill has already rewritten bad comments in place; the developer reviews the rewrites with `git diff` and opens the report for the items that need their judgment. They read it once, beside their editor, and close it.

## Product Purpose

List only what the skill could not decide alone, so the developer can judge each item fast: a comment that disagreed with its code (was the code the bug?), a badly named method or variable (rename it?), a `TODO`/`FIXME` (still needed?), commented-out code (delete it?). Ordinary rewrites stay out of the report; `git diff` shows them.

## Positioning

The code in the report is read from the files by the script, never typed by the agent, so what the developer judges is the real code.

## Operating Context

- A whole-repo run can produce hundreds of items, mostly `TODO`s; the report must stay findable at that size.
- Items are grouped into the four kinds, each with its count (shown even when 0); inside a kind, items are grouped by file so each path is written once. Each item is a collapsed row (file:line range and a one-sentence explanation) that opens to the full method or property the comment belongs to; for a long class or interface, only the declaration and member signatures. A mismatch item also shows the old comment, which the agent passes in because the file has already been rewritten.
- The header gives the repo name, the scanned path, the run time, and the four counts.
- Report language follows the majority language of the scanned comments: Traditional Chinese or English labels; any other language uses English. The explanation sentences use the same language.
- No "mark as done" state and no expand-all control: the report is read once and thrown away.

## Capabilities and Constraints

- One self-contained HTML file written to the OS temp folder as `clean-comments-<repo>-<timestamp>.html`; nothing fetched, works offline.
- Code is syntax-highlighted with highlight.js vendored in the skill (`vendor/`) and inlined into the report. Any programming language may appear.
- Light and dark follow the system setting.
- Generated by a Node script from a findings list the agent writes; tests in `tests/clean-comments/` run with `node --test`.

## Evidence on Hand

No real run exists yet; design previews use a synthetic findings list, labelled as such.

## Product Principles

1. Only what needs a human decision is in the report.
2. The code shown is the real code, read from disk.
3. Findable at hundreds of items.
4. Offline and self-contained: one file, nothing fetched.

## Accessibility & Inclusion

Dark mode is a first-class mode. zh-TW on Windows is the release check.

# Product: show-grill-clearly questionnaire

Covers the one HTML questionnaire the `show-grill-clearly` skill (`skills/engineering/show-grill-clearly/`) builds when a grilling session has decisions that are hard to follow in chat. Its visual design is recorded in its surface brief and the template itself, not in DESIGN.md.

## Platform

web

## Users

- **A developer in the middle of a grill session with an agent**: the agent has several open decisions about their own work; the questionnaire opens in the desktop browser beside the chat. Often six or more questions in one round. They decide each one, sometimes add a note instead of or beside a choice, then copy a reply prompt back into the chat.

## Product Purpose

Make every open decision clear enough to answer without the chat transcript, and turn the answers into a reply prompt the agent can act on without guessing. Success: the developer answers every question they can, knows which ones are still blank, and pastes one prompt back.

## Positioning

The questionnaire collects decisions; it never makes them. A recommendation is shown but never preselected, and a blank question stays open in the reply prompt.

## Operating Context

- Each question carries: id, title, the rewritten source question, 1–3 context facts, one scenario, 2–4 options each with a consequence note, optional recommendation, required flag. Above the questions: title, one-sentence lede, up to six confirmed facts (recap).
- Answers are a single choice per question plus an optional free-text note.
- The reply prompt's wording and rules are part of the contract with the agent.
- Opened as a `file://` page; drafts persist in `localStorage` when the browser allows it, and the page says so when it does not.

## Capabilities and Constraints

- One template, `assets/questionnaire-template.html`, is the renderer, the interaction, and the payload validator; the builders (`scripts/build-questionnaire.ps1`, `.sh`) only inject the JSON payload into its `questionnaire-data` script tag and open the result.
- Payload fields, limits, and validation messages are fixed by the skill; markup, styling, and interaction may change.
- Single self-contained file, nothing fetched, works offline. Light and dark follow the system.
- User-facing text is Traditional Chinese; zh-TW on Windows is the primary case.
- An invalid payload renders an error page with a copyable error list, never a half questionnaire.

## Evidence on Hand

No committed real payload; design previews use a synthetic payload, labelled as such.

## Product Principles

1. The original question stays intact and decidable on its own.
2. Recommendations advise, never decide; blanks stay open.
3. Findable at many questions: where you are and what is still blank is always visible.
4. Offline and self-contained: one file, nothing fetched.

## Accessibility & Inclusion

Dark mode is a first-class mode. Every answer is reachable by keyboard.
