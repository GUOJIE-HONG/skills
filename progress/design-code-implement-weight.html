design-code-implement：哪裡是核心、哪裡是重量

來源：design-code-implement/SKILL.md。黑字是這個 skill 存在的理由，橘字「＋」是為了防呆額外加上的規則。

核心步驟＋ 額外重量需要你決定提前結束

§1 收集輸入

  • 接受 spec（檔案、上游交接、對話都行），只讀使用者指到的
  • 一句話重述目標，模糊就確認
↓

§2 決定探索面向

  • 從 §1 確認的需求自己挑要探索的架構面向
  • 必含領域用語
  • 只看架構慣例，不看命名、排版
  • 最多 5 個；超過代表需求該拆
  • 只看需求碰到的區域 + git log 熱點
↓

§3 派 sub-agent 平行探索

  • 每條回報三欄：現有慣例 / 檔案:行號 / 衝突
  • 工具優先序：知識圖 MCP → repo 導覽工具 → 內建搜尋
↓

§4 產出 ≥3 方向

  • 方向 1 = 全照舊、最保守
  • 方向 2、3 = 從衝突長出來
↓

每個方向的格式

  • 4 欄位：定位 · 影響範圍 · 成本 · 何時是錯的選擇
  • 最後給一個推薦
撐不起 3 個真方向？
直說「慣例已決定做法」，停止。不湊數。
↓

你決定 選方向

  • 選一個方向
  • 可混搭 → 完整重述混搭版，再確認一次
↓

§5 寫 design.md

  • 選中的方向畫成 Mermaid：跨元件用 sequenceDiagram（含 alt 出錯分支），狀態變化用 stateDiagram，都不適用就列短清單
  • 要遵守的慣例一行一條，附檔案路徑
  • 不寫落選方向，避免實作 agent 照錯的做
  • 已存在就先讀再更新，不盲目覆蓋
  • 寫之前先問使用者要放哪裡
↓

§6 回報並停止

  • 回報方向摘要 + design.md 路徑
  • 不實作、不建議下一個指令
核心11條規則，撐起「探索 → 3 方向 → 選 → 記錄」
＋ 重量11條防呆規則，分散在每一步

重量最集中的地方：§2 的 4 條探索限制，以及 §5 的 3 條寫檔規則。
